# Harness Meta

This skill is for local `harness-spec` users who have already run `harness-spec init -p <your-name>` in a project. After reading it, an AI should understand the generated local architecture, operating model, and customization entry points inside that user project, then modify the personalized workflow root and platform directories according to the user's request.

The default operating scope is local files in the user project:

- The personalized workflow root, for example `.${your-name}/`: workflow, config, tasks, spec, workspace, scripts, and runtime state.
- Platform directories: `.claude/`, `.codex/`, `.gemini/`.
- Shared skill layer: `.agents/skills/`.
- Project metadata: `package.json` or the equivalent project config that stores `harness.spec-name`.

Do not assume the user has the `harness-spec` source repository. Do not default to modifying the global npm install directory or `node_modules`.

## How To Use

1. Read `references/local-architecture/overview.md` first to establish the local system model.
2. If the request involves a specific AI tool, read `references/platform-files/platform-map.md` and the relevant platform file notes.
3. If the user wants to change behavior, read `references/customize-local/overview.md`, then open the specific customization topic.
4. Before editing, read the actual files in the user project and treat local content as authoritative.

## Current Rules

- `workflow.md` inside the personalized workflow root is the local workflow source of truth.
- `config.yaml` inside the personalized workflow root is the project-level workflow and hook configuration entry point.
- `spec/` stores the project's coding conventions and design constraints.
- `tasks/` stores task PRDs, technical notes, research files, and JSONL context.
- `workspace/` stores project-owner session journals and cross-session memory.
- Platform settings/config files decide which hooks, agents, skills, commands, prompts, and workflows actually run.
- `.template-hashes.json` and `.runtime/` are management/runtime state files. Confirm necessity before editing them.
- `harness.spec-name` in project config is the source of truth for resolving the personalized workflow root name.

## Do Not

- Do not treat upstream `harness-spec` source code as the default target for local customization.
- Do not modify the global npm install directory or `node_modules` to implement project needs.
- Do not overwrite user-modified local files with default templates.
- Do not put team-private project rules into the public `harness-meta`; put project rules in `spec/` or a project-local skill.
- Do not describe removed legacy mechanisms as current behavior.

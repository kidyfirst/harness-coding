# 代码复用思考指南

> **目标**：在创建新代码之前先停下来想一想，这段逻辑是不是已经存在？

---

## 问题是什么

**重复代码是不一致性 bug 的头号来源。**

当你复制粘贴或重写已有逻辑时：
- bug 修复不会自动同步
- 行为会随着时间逐渐分叉
- 代码库会越来越难理解

---

## 写新代码前

### 第一步：先搜索

```bash
# 搜索相似的函数名
grep -r "functionName" .

# 搜索相似的逻辑
grep -r "keyword" .
```

### 第二步：问自己这些问题

| 问题 | 如果是…… |
|------|-----------|
| 是否已经有类似函数？ | 直接复用或扩展它 |
| 这个模式是否在别处已存在？ | 遵循现有模式 |
| 这是否应该是共享工具？ | 放到正确的共享位置 |
| 我是不是在从别的文件复制代码？ | **停止**，先抽成共享实现 |

---

## 常见重复模式

### 模式 1：复制粘贴函数

**坏例子**：把一个校验函数复制到另一个文件

**好例子**：抽到共享工具中，需要时直接导入

### 模式 2：相似组件

**坏例子**：新建一个和现有组件 80% 相似的新组件

**好例子**：通过 props / variants 扩展现有组件

### 模式 3：重复常量

**坏例子**：在多个文件里定义同一个常量

**好例子**：单一事实来源，所有地方统一导入

---

## 什么时候应该抽象

**应该抽象的情况**：
- 相同代码出现 3 次以上
- 逻辑复杂到容易藏 bug
- 多个人都可能需要它

**不该抽象的情况**：
- 只用一次
- 只是很简单的一行
- 抽象本身比重复更复杂

---

## 批量修改之后

当你在多个文件里做了相似改动后：

1. **复查**：是不是所有地方都改到了？
2. **搜索**：再跑一次 grep，确认没有漏网之鱼
3. **思考**：这是不是应该进一步抽象？

---

## 易错点：不同机制产出相同结果

**问题**：当两个不同机制必须产出同一组文件（例如 init 时递归复制目录，而 update 时手工 `files.set()`），结构性改动（重命名、移动、新增子目录）通常只会自动传到“自动机制”，手工维护那条链路会悄悄漂移。

**症状**：init 完全正常，但 update 会把文件写到错误路径，或者漏掉某些文件。

**预防清单**：
- [ ] 迁移目录结构时，搜索所有仍引用旧结构的代码路径
- [ ] 如果一条路径是自动推导，另一条是手工列举，手工那条也必须一起更新
- [ ] 加一条回归测试，对比两种机制生成的结果是否一致

---

## 提交前检查清单

- [ ] 已搜索现有相似代码
- [ ] 没有应该共享却仍然复制粘贴的逻辑
- [ ] 常量只有一处定义
- [ ] 相似模式遵循相同结构
